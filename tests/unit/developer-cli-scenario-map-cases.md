# Developer CLI scenario map cases

**Edition:** Open Source. [`test_developer_cli_scenario_map.py`](test_developer_cli_scenario_map.py)
reads the "Spec 009 scenarios" table in the [Developer CLI cases](../e2e/developer-cli-cases.md).
Task 009-14.

| Case | Plain-English action | Expected result |
| --- | --- | --- |
| DCSM-01 | Read the table. | Every Spec 009 scenario, ST29 (5), ST30 (3) and ST31 (4), is listed exactly once, by story and name, and nothing else. |
| DCSM-02 | Read each scenario's "Proven by" and "Closest evidence" cells. | No closest-evidence cell is empty ("—" when there is nothing to add). A proven scenario names at least one case in "Proven by" and never starts with "Not". A scenario on the test's not-proven list (empty today: DEV-10 proves ST30 "Cloud models use API keys") starts "Not proven yet:", says in words what is missing before it names any case, and names at least one case under closest evidence. The reason is written only in the table. Because the real table has no such row today, made-up rows check the not-proven path too: a well-formed one passes, and one that doesn't start "Not proven yet:" ("Not built yet:" doesn't count), names a case before five words of reason, has an empty closest-evidence cell or names no case there fails, as does a proven row that starts "Not proven yet:". |
| DCSM-03 | Look up where each case in a "Proven by" cell runs, including those in a not-proven cell. | Each runs in CI on the current revision. Either it runs in the unit or integration shards: its own test file is in that shard, and the test that runs it carries no live or optional mark, in the module or on the test. Or the `cli-sign-in` or `coding-runtime` job of `checks.yml`, or the `live-gateway` job of `live-preview.yml`, or the `kind` job of `kubernetes-live.yml`, really runs it: one of the job's pytest commands lists its file, the test that runs it carries the marks the command's `-m` expression selects (pytest.ini's `not live` when there is none), and the job fails on a skipped case. Only real commands count: YAML and shell comments are ignored, a collect-only listing runs nothing, and `$NAME` takes the job's own env value. A case CI doesn't run belongs under closest evidence. |
| DCSM-04 | Look up each case the table names, in either column. | Each has a row in its own catalog, the one the table's intro links for its prefix (NB in the no-browser cases, DU and DU-C in the developer usage cases, and so on; KEY-09 in the coding runtime cases, unlike KEY-01 to KEY-08). The row is a table row or a list item that starts with the case. Its own test file names it: a test function named after it, or its ID in a string, such as a report entry or a declared case list. A comment never counts, so a case mentioned only in a comment (ADM-INT-02 to ADM-INT-04 today) is untested. A prefix with no known catalog fails. |
| DCSM-05 | Read the table's intro. | It links every catalog the table's cases come from. |
| DCSM-06 | Read each DEV and PSI-LIVE case the table names. | It is in its suite's `CASES`: the developer journey suite's for DEV (today DEV-01 to DEV-10 and DEV-03b), the preview sign-in suite's for PSI-LIVE (PSI-LIVE-01 to PSI-LIVE-05). A case mentioned only in another file or a comment doesn't count. |
| DCSM-07 | Change copies of the files as a careless change would: take the live mark off the admin sign-in test, change the `cli-sign-in` job's `-m` to `optional and not live`, comment the admin sign-in file out of the job's list, point a live and optional test at the shards, point a case at a file no job lists, and at a catalog with no CI job. Also look for ADM-INT-04, which is only in a comment, and for DEV-11, a case the journey suite doesn't have. | ADM-INT-01 runs in CI before the changes and in none of the changed copies. ADM-INT-04 is untested. DEV-10 is in the journey suite's `CASES` and DEV-11 isn't. |
| DCSM-08 | Read marker expressions such as `optional and live`, `not live` and `(live or optional) and not kubernetes`. | Each selects a test as pytest does: `optional and live` needs both marks, and `not live` refuses a live test. |

When Spec 009 adds or renames a scenario, update the list in the test and the
table together. When a not-proven scenario's missing check runs in CI, take it
off the test's not-proven list and name the cases. When the table
names cases from a new catalog, add the prefix, catalog, test file and CI job
to the test's list and link the catalog in the intro.
