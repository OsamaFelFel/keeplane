# Customer-run gateway behind the protected TLS edge

The [plain-English cases](../full-existing-edge-cases.md) and [repeatable verifier](../test_full_existing_edge.py) ran the pinned upstream agentgateway chart separately from Keeplane's existing-gateway chart on the isolated Calico kind cluster. A generated certificate, first-admin password and gateway keys were used only in temporary files and Kubernetes test Secrets. The verifier removed both disposable namespaces and its port-forward. The regular Docker and kind previews were not redeployed.

The [confirmed machine result](2026-10-10-full-existing-edge-confirmed.json) passed **5/5 cases**. Keeplane's own namespace contained only its app Deployment. The gateway preflight succeeded, HTTPS sign-in and identity worked, and Keeplane registered a local fixture model on the customer-run gateway and received its answer. After a customer-owned ingress policy was applied to the gateway, the app remained connected but an unrelated pod timed out before it could call the gateway. Keeplane's public TLS address redirected `/v1/models` to sign-in instead of publishing a gateway route.

The [initial run](2026-10-10-full-existing-edge-first.json) and [diagnostic repeat](2026-10-10-full-existing-edge-diagnostic.json) each failed model setup. They tried to approve `customer-fixture`, a gateway-only model that Keeplane had not registered; the diagnostic showed the app could reach the gateway but could not verify that model's definition. The final run used Keeplane's supported registration path for `customer-managed`. The [intermediate passing run](2026-10-10-full-existing-edge-registered.json) is retained; the final run tightened the public-route assertion to require the observed 302 redirect.

An [additional preflight-policy run](2026-10-10-full-existing-edge-preflight-policy.json) passed **5/5 cases** with the customer ingress policy applied **before** Keeplane installation. The chart's preflight Job now carries a stable `app: keeplane-gateway-preflight` label; the customer policy admits only that label and `app: keeplane-app` from Keeplane's namespace. This proves install and model traffic under the policy on this local Calico cluster. Namespace permissions must still stop untrusted pod creators from adopting those labels. Default-deny egress, provider-path control, project-bound identity and class enforcement, production storage, certificate operations and a customer-installable gateway artifact remain open. The release gateway remains unselected.

The [complete Docker/kind regression](2026-10-10-existing-preflight-policy-full-confirmed.json) passed **48/48 suites and 290 case records**, restored the original Data Classes mode, and both daily app-health endpoints returned HTTP 200 afterward. The [first full attempt](2026-10-10-existing-preflight-policy-full-regression.json) passed 47/48 suites: the kind Qwen script received a non-JSON response during the broader rollout and stopped before recording its cases. A [focused Qwen repeat](2026-10-10-existing-preflight-policy-qwen-recheck.json) passed 2/2, followed by the clean full result. Both attempts are retained.

The [reusable customer policy example](../../deploy/examples/customer-gateway-ingress-policy.yaml) is now the input to the verifier, rather than an inline policy. Its [confirmed repeat](2026-10-10-full-existing-edge-example-policy-confirmed.json) passed the same **5/5 cases** with the policy active before installation. The [first example run](2026-10-10-full-existing-edge-example-policy.json) stopped before cluster policy application because a comment contained invalid template syntax; that comment was corrected and the failed setup result retained. No product runtime or chart template changed for this example stage, so the targeted live repeat verifies it; the preceding full regression remains the chart-change evidence.
