# Chart installation shape cases

Run `.venv/bin/python -m pytest tests/integration/test_chart_installation_shape.py`
with Helm 3.19 or newer. The checks find Helm through `KEEPLANE_HELM_BIN`, else
`helm` on `PATH`; without Helm they are skipped, and a skipped case is not a pass.

Each case renders the chart with `helm template` in four installations: PostgreSQL
with the managed gateway, PostgreSQL with an existing gateway, and the two local
trial values in `deploy/local/`. The PostgreSQL values are written to a temporary
file and use the documented Secret-backed gateway settings. SHAPE-08 to SHAPE-13
also render deliberately incomplete or invalid variants. Rendering proves what
the chart asks Kubernetes to create. It does not prove that a cluster enforces it.

| ID | Plain-English action | Expected result |
| --- | --- | --- |
| SHAPE-01 | Render both PostgreSQL installations and both local trials, then set the managed gateway image to a tag or to a registry/repository/tag map. | In PostgreSQL installs, every image is `repository@sha256:<digest>`. The local trials use a tag only for the locally built app image, as the chart allows; the gateway image stays pinned. A managed gateway image without a digest is refused in PostgreSQL mode. Existing-gateway mode ignores that setting. The gateway chart dependency has an exact version and a lock digest. |
| SHAPE-02 | List every Service, Ingress backend and declared container port. | The app Service has only port 3000. In managed mode the `ClusterIP` gateway Service and the headless `<release>-gateway-copies` Service, which gives each gateway copy its own address, each have only port 4000. No Service or container port uses the gateway's admin (15000), stats (15020) or readiness (15021) ports, and the chart does not move those listeners. The Ingress routes only to the app Service on port 3000. Existing-gateway mode has only the app Service. |
| SHAPE-03 | Turn on the gateway NetworkPolicy in the managed PostgreSQL installation. | One policy selects this release's gateway pods, including every gateway copy, and admits only pods labelled as this release's app, on TCP 4000. It has no namespace or address-range rule. The migration Job does not carry the admitted label. The policy is off by default and absent in existing-gateway mode. |
| SHAPE-04 | Inspect every container's environment and mounts, the gateway configuration and connection URLs. | The chart renders no Secret object. Each password, key or signing secret is either a `secretKeyRef` or a path to a file in a read-only Secret mount. The gateway configuration contains only `${...}` placeholders for its database password and key hashes, each loaded from a Secret. No URL contains a literal password. The existing-gateway app receives no gateway database credential. |
| SHAPE-05 | Inspect every Deployment's and StatefulSet's probes, root filesystem and writable mounts. | Every long-running container has a readiness probe and a read-only root filesystem. The app also has a liveness probe; the gateway has a startup probe. In PostgreSQL mode the only writable app state is the operator's provider-key claim. The local trials declare their state and provider-key claims. The gateway writes only scratch `/tmp` and keeps its catalog in PostgreSQL. The app and the gateway copies each run twice in the managed PostgreSQL installation; the bundled gateway chart's own Deployment runs none. Jobs are bounded install hooks. |
| SHAPE-06 | Render existing-gateway mode while full managed-gateway settings, including an extra model, are still in the values. | Only the Keeplane app, its Service, Jobs, Ingress or trial claims render. No gateway Deployment, Service, configuration, account or policy appears, and the extra model is not written anywhere. The app points at the supplied gateway URL and gets no managed gateway configuration file. |
| SHAPE-07 | Render the managed PostgreSQL installation and the managed local trial with `gateway.keysSecret` set, without writing any key policy in the values. | The gateway configuration requires a key for management (`ui`) and for model calls (`llm`) on port 4000: each is a strict policy with one `${...}` placeholder. The gateway reads both hashes with `secretKeyRef` from the Secret named in `gateway.keysSecret` (`runtime-key-hash` and `admin-key-hash`). The chart renders no Secret object and no literal key hash. Neither the test values nor `deploy/local/values.yaml` repeat the policy. |
| SHAPE-08 | Try to install the managed gateway without `gateway.keysSecret` (bare default install, minimal values, PostgreSQL values, local values), without its hash variables, with a hash from another Secret, a literal hash or a duplicate variable, and with the model policy removed, the management policy loosened or an extra model key added. | Helm refuses every one before installation. Without the Secret the message tells the installer to create it and set `gateway.keysSecret`. A missing or wrong hash variable names `gateway.keysSecret` and the exact `extraEnv` entry to add. A weakened policy names the policy the chart sets. |
| SHAPE-09 | Render existing-gateway mode with no `gateway.keysSecret`, and with gateway values that have no key policy or hash variables. | Both render. No managed gateway object appears and no managed-gateway key message is shown; a customer-run gateway keeps its own key setup. |
| SHAPE-10 | Render the managed PostgreSQL installation with the default two gateway copies, with three (NetworkPolicy on) and with one. Then try zero copies, 33 copies, the bundled chart's own replica count set to 2, its autoscaling turned on, and a supplied copy list in managed mode. | The gateway copies run as a StatefulSet with exactly `gateway.copies` replicas behind the headless `<release>-gateway-copies` Service on port 4000. The app's `GATEWAY_COPY_URLS` lists exactly one private address per copy, `http://<release>-gateway-<N>.<release>-gateway-copies.<namespace>.svc:4000`, in order. The bundled Deployment has zero replicas. The gateway NetworkPolicy selects the copies. Helm refuses every invalid variant and names the setting. |
| SHAPE-11 | Render existing-gateway mode with a supplied list of two copy addresses and with one `https` address. Then supply entries with credentials, a path, a query, another scheme, a space, two addresses in one entry, a repeated entry, and 33 entries. | The app's `GATEWAY_COPY_URLS` is the supplied list, joined with commas, and no gateway object renders. Helm's values check refuses every invalid list before installation and names `copyUrls`. Without a list (SHAPE-06) the app gets no `GATEWAY_COPY_URLS`. |
| SHAPE-12 | In the managed local trial, set the gateway image as a registry/repository map with the bare tag `1.6.0` and pull policy `Always`, then with no tag. In the managed PostgreSQL installation, add a `config.modelCatalog` entry, replace the model list, and change the gateway database address. | The gateway copies use exactly the image and pull policy the bundled gateway chart renders: `cr.agentgateway.dev/agentgateway:v1.6.0` in both cases (a bare version gets its `v`; no tag means the bundled chart's version). The copies' restart hash always equals the bundled chart's. The catalog entry and the model list leave it unchanged, so those changes do not restart the copies; the database change alters it. |
| SHAPE-13 | In the managed PostgreSQL installation, turn on `agentgateway-standalone.podDisruptionBudget` with the default two copies, with `maxUnavailable: 1`, and with one copy. Then turn on `agentgateway-standalone.monitoring`. | With two copies one disruption budget, `<release>-gateway`, selects the gateway copies: `minAvailable: 1` by default, or `maxUnavailable: 1` when set. With one copy, or with the budget off, none renders. Helm refuses monitoring and names `agentgateway-standalone.monitoring`: the copies declare no metrics port, which stays private. |

Not covered here: live NetworkPolicy enforcement, readiness under failure,
storage behaviour, and a live call proving the running gateway refuses a missing
key. Those run in the Kubernetes regression (see the
[installation reference](../../docs/guide/kubernetes-installation-reference.md)).
No live check yet reads a model back from each gateway copy's own address.
