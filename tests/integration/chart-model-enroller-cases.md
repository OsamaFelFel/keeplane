# Chart model enroller cases

Run `.venv/bin/python -m pytest tests/integration/test_chart_model_enroller.py`
(tasks 004-01 and 002-02, Spec 004 ST10 and ST23–ST25, Spec 002 ST1, ST4 and
ST5, [ADR 027](https://github.com/OsamaFelFel/keeplane-governance/blob/main/adrs/0027-model-enroller.md)).
All cases but ME-10 render the chart with `helm template --namespace keeplane`
and need Helm 3.19 or newer, found through `KEEPLANE_HELM_BIN`, else `helm` on
`PATH`. Without Helm they are skipped, and a skipped case is not a pass. ME-10
reads only the values file and the guides and always runs.

With the enroller on, the chart also installs Keeplane's protected runtime on
every managed gateway copy (ME-11 to ME-13): the init step writes the runtime
into the copy's guard from the chart's own gateway configuration, and the
gateway starts from it. The refusal the chart carried until then
(`templates/checks/first/protected-runtime.yaml`) is gone; every other refusal
stays (ME-09).

Installs use the managed PostgreSQL values of the
[installation shape cases](chart-installation-shape-cases.md), release `pg`,
with the enroller settings the
[installation reference](../../docs/guide/kubernetes-installation-reference.md#model-enroller)
shows. Those values turn on the gateway ingress policy, so they also name the
ingress controller's namespace in `networkPolicy.publicEntry`, which the
enroller then needs. The init step itself is
[EF-01 to EF-13](../unit/model-enroller-files-cases.md). How developers reach
the protected runtime is in the
[protected access cases](chart-protected-access-cases.md).

| ID | Plain-English action | Expected result |
| --- | --- | --- |
| ME-01 | Render managed and existing-gateway PostgreSQL installs and both local trials with the default values. | Nothing about the enroller renders: no `KEEPLANE_GUARD_STATUS_CHECK`, enroller container, init step, guard folder, `/installed` mount, callback key or `configure_guard_status_access`. The managed copies start from the ConfigMap's `/config/config.yaml`, as before. |
| ME-02 | Turn the enroller on. | Each gateway copy Pod runs `agentgateway` and `model-enroller`, after the init step `prepare-model-enroller`; there are still two copies and no API token. The enroller runs `manage.py run_model_enroller --callback-host pg-app:3000` from the app image, declares no port or probe, runs as user 65532 with a read-only root, no privilege, no escalation, every capability dropped and the runtime's default seccomp profile, and has CPU and memory requests and limits; so does the init step. It reaches the gateway on `127.0.0.1:4000`, reads approvals as `keeplane_enroller` with `KEEPLANE_DATABASE_READ_ONLY=1` and `verify-full`, takes its copy name from the Pod name, and reads every credential from a file under `/run/keeplane-enroller/files`, never from a setting. It mounts the guard read-write at `/installed`, its files and the provider-key claim read-only. |
| ME-03 | Compare the copies with the enroller off and on, and read the app. | The gateway container gains only a read-only mount of the guard at `/installed` and starts from `/installed/gateway.json` instead of `/config/config.yaml`; its other settings, image and security are unchanged. The Pod gets no `fsGroup` and no Secret or projected volume: the guard is a 16Mi `emptyDir`, the enroller's files a 1Mi in-memory `emptyDir` that only the init step and the enroller mount, and the provider-key claim is mounted read-only by the enroller only. The app Deployment mounts no guard, nothing at `/installed` and none of the enroller's volumes. |
| ME-04 | With one, two and three copies, list where the init step's values come from. | Exactly: `password` of the approvals Secret, `copy-<N>-password` of the status Secret for every copy, `ca.crt` of `app.postgres.caSecret`, and `admin-key`, `runtime-key`, `callback-key`, `admin-key-hash` and `runtime-key-hash` of `gateway.keysSecret`, none optional. Every copy's status password reaches each Pod's short-lived init step; the running enroller gets only its own (EF-01). The copy prefix is `pg-gateway-` and the status roles are listed in copy order. The trusted base is a plain setting. The app's database Secret, the identity Secret and the migration Secret appear nowhere in the gateway Pod, and the gateway database Secret not in the init step. |
| ME-05 | Turn the enroller on; then also ask for the check; then turn the check off while the enroller runs. | The app container gets `KEEPLANE_GUARD_STATUS_CHECK=1` in all three, and no other object gets it. |
| ME-06 | Turn the enroller on with three copies, then with CLI sign-in too. | The migration Job runs `migrate`, then `configure_guard_status_access` with the app role, the approvals role and `pg-gateway-0` to `pg-gateway-2` paired with their status roles. With CLI sign-in the client registration runs between them. |
| ME-07 | Turn on the egress policies, then the app ingress policy, with and without the enroller. | With it, `pg-gateway-egress` gains exactly the `networkPolicy.egress.postgres` rule and then a rule to this release's app pods on TCP 3000, after its existing rules, and `pg-app-ingress` gains exactly one rule admitting the gateway copies on TCP 3000; without it, neither has those rules. |
| ME-08 | Give the app a pull secret and turn the enroller on. | The same objects render as without it plus two: Service `pg-gateway-runtime`, the protected port's address ([PA-02](chart-protected-access-cases.md)), and Ingress `pg-gateway-runtime`, the protected path on the chart's host ([PA-03](chart-protected-access-cases.md)); no new kind. The gateway copy Pods get the app's pull secret, which they didn't before. |
| ME-09 | Try unsafe or incomplete settings: the enroller or the check with `gateway.mode=existing`; the check without the enroller; either on the local trial (no PostgreSQL); a missing or upper-case approvals role; too few status roles or more copies than roles; a role with a dash; a shared status role; the approvals role equal to the app role, or a status role equal to the migration role; a missing approvals or status Secret; the app's database Secret or the gateway keys Secret as an enroller Secret; no limits, or no memory limit; an extra gateway volume named `keeplane-guard`; an extra mount at `/installed/` or `/installed/keys`; a gateway container or Pod `runAsUser` other than 65532; a 53-character release name with 32 copies; unknown keys or wrong types under `gateway.enroller`; the check as text. | Helm refuses each one, with a message naming the setting and why: the managed-gateway rule, "can be on only together with the model enroller", "needs app.postgres", "must name", "gateway.copies is 2, but 1 roles are listed", "statusRoles[1]", "needs its own roles", "is required", "must be Secrets of their own", "limits needs cpu and memory", the reserved volume name or path, the gateway user, and "must be at most 63 characters" naming `…-gateway-31`. A read-only gateway (`agentgateway-standalone.mode=readonly`) is refused with "needs agentgateway-standalone.mode=database", and an admin address other than loopback with the address named. The same long release name with 10 copies renders, and so do a gateway that sets `runAsUser: 65532` and one that sets `adminAddr: 127.0.0.1:15000`. The values schema refuses the wrong keys and types. |
| ME-10 | Read `values.yaml`, the installation reference's Model enroller section, the roles guide and the runtime authorization page. | The values file has `gateway.enroller.enabled: false`, `app.guardStatusCheck: false` and comments for every enroller setting. The reference no longer says Helm refuses the enroller; it describes the protected runtime (`callback-key`, `/installed/gateway.json`, `agentgateway-standalone.mode=database`, port 5000) and names every value and Secret key, `KEEPLANE_GUARD_STATUS_CHECK`, `configure_guard_status_access`, the existing-gateway refusal, `secretKeyRef`, no port, user 65532, `networkPolicy.egress.postgres` and the restart a rotation needs. It also names the two limits on the trusted base: the gateway database password as a `${KEEPLANE_DB_PASSWORD}` variable in `agentgateway-standalone.database.postgres.url` (linking `gateway-database-secret.md`), and `KEEPLANE_ENROLLER_RUNTIME_BASE` within 120 KiB (122880 bytes). The roles guide links to it and the runtime authorization page names `gateway.enroller`. |
| ME-11 | Turn the enroller on with the managed gateway and PostgreSQL; then with an existing gateway, the check alone, and the enroller on the local trial. | The chart has no `templates/checks/first/protected-runtime.yaml` and renders the enroller, with `KEEPLANE_GUARD_STATUS_CHECK=1` on the app. The others are still refused: "applies only to the managed gateway", "can be on only together with the model enroller", "needs app.postgres". |
| ME-12 | Read the trusted base the init step gets, run it through the init step's own preparation, then render a key rotation and a changed model. | The base is the bundled chart's configuration: the database storage and address, port 4000, both strict key policies naming `${GATEWAY_ADMIN_KEY_HASH}` and `${GATEWAY_RUNTIME_KEY_HASH}`, the installer's model, and `adminAddr: 127.0.0.1:15000`. The init step turns it into a disabled declaration, the callback key and identical `trusted.json` and `gateway.json` with the hashes written out and the gateway database password left as a variable. With a rotation's next hashes, the init step also gets `admin-key-hash-next` and `runtime-key-hash-next`, which it doesn't otherwise, and refuses the base without them. A changed model changes the base, so the copies restart from it. |
| ME-13 | Turn the enroller on and read the app. | The app gets `RUNTIME_AUTHORIZER_KEY_FILE=/run/gateway-keys/callback-key` and no guard manifest setting; without the enroller it gets neither. |
| ME-14 | Turn the enroller on with the gateway database password written literally in `agentgateway-standalone.database.postgres.url`: after the user name (with `postgresql://` or `postgres://`), beside a `${...}` variable, as a `password` or `sslpassword` parameter, after the user name with an `@` also in a query value, with a `?` or `#` inside it, with a `/` and then a `?` or `#` inside it (also under an upper-case `POSTGRESQL://` scheme), or with no database path; a percent-encoded parameter name such as `pass%77ord`; a numeric password followed by `/`, `?` or `#` and then an `@` (`u:20261102/x?y@h/db`, which an authority parser reads as a port but a library taking the first `@` reads as a password), or with an `@` only in a later query value; with no user name, an `@` in a query value or after a `#` (also with an IPv6 host); a `password`, `sslpassword` or `pass%77ord` parameter after a `#` in the query (`?x=1#&password=…`, `?application_name=x#y&password=…`), which libraries without fragments still read; and an `@` after a `#` in the database path. Then use the variable form the guides show, a `${GATEWAY_DB_PASSWORD}` variable, a URL with no password, a variable `sslpassword`, an `@` in a query value (`application_name`) after the variable password, after the user name alone and with a bracketed IPv6 host, a `#` in a query value that sets no password, and a `%40` in a query value with no user name; then the literal URL without the enroller. | Helm refuses each literal form with "gateway.enroller needs the gateway database password", naming `agentgateway-standalone.database.postgres.url`, the form `postgresql://keeplane:${KEEPLANE_DB_PASSWORD}@…` and `docs/guide/gateway-database-secret.md`, and the refusal never repeats the password. The variable forms, the URL with no password and the URLs with a second `@` only in a query value render, and the trusted base carries the URL as written. Without the enroller the literal URL renders as before. |
| ME-15 | Turn the enroller on with 1200 models in `agentgateway-standalone.config`; render the same without the enroller; then turn it on with 100 models. | Helm refuses the first, naming `KEEPLANE_ENROLLER_RUNTIME_BASE`, the 128 KiB limit Linux puts on one environment value, the rendered size (over 122880 bytes) and the chart's limit of 122880 bytes (120 KiB), and says to shorten `agentgateway-standalone.config`. Without the enroller it renders; with 100 models it renders and the base holds all 100 within the limit. |

Not covered here: rendering proves what the chart asks Kubernetes to run, not
a live run. Whether the real gateway image reports its starting configuration
exactly as the trusted base (including the gateway database address it reads
from its environment) is checked only by a live run; if not, enrolment fails
closed and the copy's protected models stay refused. A live install, the
files the kubelet writes, a NetworkPolicy that a plugin enforces, and a run on
the real gateway image have not run.
