# Chart protected access cases

Run `.venv/bin/python -m pytest tests/integration/test_chart_protected_access.py`
(tasks 004-01 and 002-02, Spec 004 ST10 and ST23–ST25, Spec 002 ST1 and ST4,
[ADR 016](https://github.com/OsamaFelFel/keeplane-governance/blob/main/adrs/0016-control-plane-stack.md),
[ADR 018](https://github.com/OsamaFelFel/keeplane-governance/blob/main/adrs/0018-gateway-runtime-policy.md),
[ADR 027](https://github.com/OsamaFelFel/keeplane-governance/blob/main/adrs/0027-model-enroller.md)).
All cases but PA-06 and PA-09 render the chart with `helm template --namespace keeplane`
and need Helm 3.19 or newer, found through `KEEPLANE_HELM_BIN`, else `helm` on
`PATH`. Without Helm they are skipped, and a skipped case is not a pass. PA-06
and PA-09 read only the values file, the guides and the CLI code and always run.

With the model enroller on, each managed gateway copy runs Keeplane's
protected runtime, whose listener is port 5000 with one route,
`POST /v1/chat/completions`. These cases check how developers' CLIs reach it:
through Keeplane's one public address, on one exact path, with every gateway
management port private. Installs use the managed PostgreSQL values of the
[installation shape cases](chart-installation-shape-cases.md), release `pg`,
with the enroller settings of the
[model enroller cases](chart-model-enroller-cases.md). The guide is
[how developers reach protected models](../../docs/guide/kubernetes-installation-reference.md#how-developers-reach-protected-models).

Rendering proves what the chart asks Kubernetes to create. It does not prove
that a cluster routes or enforces it: a live run through an ingress controller
and a NetworkPolicy-enforcing plugin, on the real gateway image, is not part of
these cases.

| ID | Plain-English action | Expected result |
| --- | --- | --- |
| PA-01 | Render the managed and existing-gateway PostgreSQL installs and both local trials with the default values. | No `-gateway-runtime` Service renders, no Service carries port 5000, no Ingress path is `/v1/chat/completions` or goes to port 5000, and nothing renders `port: 5000`. |
| PA-02 | Turn the enroller on and list every Service and declared container port. | One new Service, `pg-gateway-runtime`: an ordinary `ClusterIP` (not headless), selecting exactly the gateway copies' pod labels, with one port, `protected`, TCP 5000 to 5000. The Services are then exactly `pg-app` (3000), `pg` (4000), `pg-gateway-copies` (4000) and `pg-gateway-runtime` (5000): no other Service gains 5000 and none carries the admin (15000), stats (15020) or readiness (15021) port. The declared container ports are the same as without the enroller. |
| PA-03 | With the enroller and the chart's Ingress (plus an `ingress.annotations` entry), read the Ingresses; then turn the Ingress off. | Two Ingresses, `pg-app` and `pg-gateway-runtime`, on the one host with the same class and TLS Secret, one rule each. `pg-app` has only `/`, `Prefix`, to `pg-app` port 3000; `pg-gateway-runtime` has only `/v1/chat/completions`, `Exact`, to `pg-gateway-runtime` port 5000, so only one Ingress claims that path. The annotation is on `pg-app` only; `pg-gateway-runtime` has none. No path goes to 4000, 15000, 15020 or 15021. With the Ingress off no Ingress renders and the Service still does, for an installer's own edge. |
| PA-04 | Turn on the gateway ingress policy with an ingress controller's namespace and pod labels in `networkPolicy.publicEntry`, without and with the enroller; then with pod labels only; then also the app ingress policy. | Without the enroller the policy admits only this release's app pods on TCP 4000, as before. With it, it also admits exactly the public entry's namespace and pod labels on TCP 5000, and nothing else; the app pods still reach only 4000. With pod labels only, the 5000 rule stays inside the release namespace. The app ingress policy still admits only TCP 3000. |
| PA-05 | Turn on the enroller and the gateway ingress policy with an empty `publicEntry`, then with empty label maps; then turn the policy off; then render the gateway policy without the enroller and with no `publicEntry`. | Helm refuses the first two, with a message naming `gateway.enroller with networkPolicy.gatewayIngressEnabled needs networkPolicy.publicEntry` and port 5000. Without the gateway policy it renders. Without the enroller the gateway policy needs no public entry, as before. |
| PA-06 | Read `values.yaml` and the installation reference. | The values file names `<release>-gateway-runtime`, `/v1/chat/completions`, `https://<ingress.host>/v1`, `TCP 5000` and `protectedIngress`, says `ingress.annotations` stay on the app's Ingress, and no longer says the Ingress publishes only the app. The reference's Model enroller section explains the Service, the protected path's own Ingress and exact path, `gateway.protectedIngress.annotations` (with `proxy-read-timeout`), `https://<host>/v1` as the CLI's gateway, saved at sign-in or given as `--gateway`, `networkPolicy.publicEntry` and ADR 016; its Ports section names the Service and path. It no longer says the port has no Service, that how developers reach it is not decided, that the gateway is never an Ingress backend, that the Ingress routes only to the app, or that `ingress.annotations` apply to the app and protected path alike. |
| PA-07 | With the enroller and the chart's Ingress, read both Ingresses' annotations: by default; with `ingress.annotations` (body size 1m) and `gateway.protectedIngress.annotations` (read timeout 190, body size 16m); with only the latter. Then set the latter without the enroller, then turn the Ingress off; then give an annotation a number, or `protectedIngress` another key. | By default neither has annotations. Each value reaches only its own Ingress: `pg-app` gets exactly `ingress.annotations`, `pg-gateway-runtime` exactly `gateway.protectedIngress.annotations`, so the model path's timeout and body size leave the app's `/` as it is. Without the enroller only `pg-app` renders, without annotations; with the Ingress off neither does. Helm's schema refuses the number and the extra key, naming `protectedIngress`. |
| PA-08 | Set `networkPolicy.publicEntry` to null, in a values file and with `--set networkPolicy.publicEntry=null`: with the enroller and the gateway ingress policy, and with the app ingress policy alone. Then with the gateway policy and no enroller, and the enroller with no gateway policy. | The first four are refused with the chart's own messages (`gateway.enroller with networkPolicy.gatewayIngressEnabled needs networkPolicy.publicEntry`, or `networkPolicy.appIngressEnabled needs networkPolicy.publicEntry.namespaceSelector or podSelector`), never a template nil-pointer error. Where nothing needs a public entry, null renders. |
| PA-09 | Read the reference's "What to give developers" and the CLI quickstart, and give the CLI's coding command gateway addresses. | The reference gives `https://<host>` for `keeplane login --server` and says the coding address `https://<host>/v1` is saved at sign-in, with `keeplane code --gateway` overriding it; it says the chart sets `KEEPLANE_GATEWAY_PUBLIC_URL` to `https://<ingress.host>/v1` and the server gives it as `gateway_url` on `GET /api/runtime/session` (`null` when unset), that the CLI saves it in the developer's profile at sign-in and a resumed session needs the same one, and names what the chart publishes without the enroller or with a customer-run gateway; the quickstart gives the server address and the gateway `https://<host>/v1`, says the CLI saves the gateway in the profile for `keeplane code`, and says a resumed session uses the same gateway. The profile checks the saved gateway with the CLI's own gateway check, `keeplane code` takes it from the profile, records it in the session history's binding, and `--gateway` overrides it. The check takes `https://keeplane.example/v1` (with or without a final `/`) and `http://127.0.0.1:5000/v1`, and refuses the bare host, `/v1/chat/completions`, a query and `http` to another computer. |
| PA-10 | With the enroller and the chart's Ingress, read the app's settings; then render without the Ingress, without the enroller, with a customer-run gateway and both local trials (task 009-02, ADR 030). | The app alone gets `KEEPLANE_GATEWAY_PUBLIC_URL=https://keeplane.example.test/v1`, the protected Ingress's host followed by `/v1`, which the server keeps unchanged and the CLI's `--gateway` check accepts. Every other install sets no address, so the server answers that it doesn't know one. |
